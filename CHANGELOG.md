# Changelog

## 1.0.0
- Initial release.
- Reads the whole project. A code index finds every function, route, data shape (DTO), business rule and entry point without the model, and a pr-agent-style packer shows the model the most important files whole and the rest as outlines, instead of skipping them. Diffs are compressed the same way.
- One coee column: every coee page opens as a tab in one group beside your code, with the same switcher on each page.
- Walkthroughs: explain lines, a function, a file or a folder step by step beside the code, with flow, sequence and state diagrams. coee plans the steps itself: Start here, then every function, class and method in the order the code runs, with exact lines, then how it fits together; nothing is skipped. Each step highlights exactly its code (decorators and doc comment included; braces in strings, regexes and comments don't confuse it; functions are never split across parts) and marks its 1-3 key lines with notes, in the editor too. Written for beginners by default (coee.audience). Each step shows what it takes and gives, its rules, and Calls / Called by links to other steps. Each can be made simpler, deeper or line by line, or you can ask your own question. Tours start at the real entry point. The Walkthrough tab tours the project it was opened from; it never reopens an older file or selection walkthrough. Switching pages from a file walkthrough opens the project holding that file, instead of failing with spawn ENOTDIR.
- Beyond web APIs: UI and app events (DOM, React, Vue, Angular, Svelte, Android, Compose, Flutter, SwiftUI, UIKit, Swing, JavaFX, Qt, Tkinter, WinForms, Electron, sockets, CLI commands, timers) are indexed like routes. Top-level handlers get walkthrough steps of their own, and the architecture page has a UI & events section. Entry points cover React, Flutter, Android, Spring Boot, JavaFX, Swing, SwiftUI, Electron, desktop UI loops and CLIs. Kotlin and Swift functions with return types are found (and calls in those languages, which have no semicolons, are no longer taken for methods; SwiftUI `body` and `init` get steps, and SwiftUI and UIKit button actions count as events), and HTML, FXML, XAML, QML and .kts files are read. Walkthroughs explain each kind of code in its own terms: requests for servers, what the user sees and does for UIs, arguments and output for CLIs.
- Mobile screens: Android layout XML (only `res/layout*`, `res/navigation*` and `res/menu*`, never every resource) with `android:onClick` and data-binding handlers; iOS storyboards and xibs with their button actions and segues; Objective-C (`.m`, `.mm`): `@implementation` classes, methods, C functions, `#import`ed headers, `IBAction`s and `addTarget:action:` targets. The app delegate's `didFinishLaunchingWithOptions` counts as where an iOS app starts. A layout's `android:onClick="save"` or a storyboard action links to the method it calls (the screen's own Activity or view controller first).
- Mobile security checks: Objective-C files get the C memory-safety rules; new rules for secrets kept in UserDefaults or SharedPreferences, Keychain items readable while the phone is locked, and web views that expose app code (addJavascriptInterface, UIWebView); NSKeyedUnarchiver counts as unsafe deserialization, and allowInvalidCertificates or proceeding past an SSL error counts as TLS checks turned off.
- Mobile and JVM projects in the security scan: dependency advisories from OSV.dev for Gradle (build.gradle, build.gradle.kts and the libs.versions.toml version catalog), Maven (pom.xml), Flutter and Dart (pubspec.lock) and Swift packages (Package.resolved), each pointing at the line that declares the package. App settings checks: in AndroidManifest.xml, debuggable builds, plain HTTP, backups, components any app can start (content providers rated high) and deep-link screens; in network_security_config.xml, plain HTTP and trusted user certificates; in Info.plist, App Transport Security turned off or excepted. The model also follows input from other apps and the system (deep links, intents, exported components, web views, the clipboard) and checks how secrets are stored. Prove it runs proof tests with Gradle (module-aware, Android included), Maven, swift test and flutter test or dart test, saved in each tool's test folder. Gradle, Maven, CocoaPods, Swift package, Flutter, Android and iOS manifests are read as project files.
- Key lines are placed by the code they quote, not only by line number, so a number that's one off never marks the wrong statement, a blank line or a brace.
- Architecture overview: where execution starts, the API (routes, handlers, data, guards), business rules in plain words by part, data shapes with fields and where they're used, and for each use case the rules it applies; plus how the project works, every component and how they connect, use cases with sequence diagrams, lifecycles as state diagrams, and the data model as an ER diagram. **Walk me through** starts a walkthrough for any component or use case, and the page follows the walkthrough as it moves. File links select the exact lines. **Find** answers where something is handled, and big repositories start at their packages.
- Changes: a live review of your git changes, with fast checks on every save and model reviews on stage or save. Each file is reviewed with the call sites of what it changed, then the whole change gets a second pass across files; low-confidence findings are dropped. Findings appear as comments on the lines, in the Problems panel and in the status bar, with suggestions you can apply. Also includes a suggested commit message, branch vs main, and explaining any commit.
- Plan a change: integration points, affected components, risks and an order of work, against your real code, with the code to add and always its tests. Snippets are placed by the code around them, previewed, checked after adding, and never added twice.
- Security scan: for a file, folder or project, covering every OWASP Top 10 (2021) category (61 rules plus whole-project design checks for missing auth, rate limits and security headers), with an OWASP grid on the page. Fast rules, then dependency advisories (npm audit, pip-audit or OSV.dev), then the model confirms each finding and finds logic flaws. Findings are grouped by OWASP category, each with the attack's path through the code (source to sink, with where to validate), a step-by-step attack walkthrough, an attack diagram and a fix. Prove it runs a proof test with the project's own test runner, after a confirmation, to show the attack works and that the fix stops it. Also adds Problems panel entries with quick fixes, dismissals and SARIF export.
